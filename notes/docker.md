## 📖 Теоретический минимум

> [!info] Ключевые понятия
> - **Образ (Image)**: Неизменяемый шаблон, содержащий инструкции для создания контейнера. Можно представить как "класс" в ООП.
> - **Контейнер (Container)**: Запущенный экземпляр образа. Это "объект" класса. Он имеет изменяемое состояние (read-write слой поверх образа).
> - **Слой (Layer)**: Каждый результат выполнения инструкции в `Dockerfile` (например, `RUN`, `COPY`, `ADD`) создает новый слой. Слои кэшируются. Если инструкция и её контекст не изменились, Docker возьмет результат из кэша, что ускоряет сборку.
> - **`.dockerignore`**: Аналог `.gitignore`. Указывает Docker, какие файлы и папки **не** нужно копировать в контекст сборки. Это критически важно для уменьшения размера образа и ускорения сборки.

> [!tip] 💡 Золотое правило оптимизации
> Инструкции, которые меняются редко (например, установка зависимостей `pip install`), должны находиться **выше** в Dockerfile, чем инструкции, которые меняются часто (например, `COPY . .` с исходным кодом). Это максимизирует использование кэша.

## 🏗️ Сборка и управление образами (Images)

### Проверка установки
```bash
docker --version
docker info
```

### Сборка образа
```bash
docker build -t <имя-образа> .
```
> [!warning] ⚠️ Частая ошибка новичка
> **Точка в конце обязательна!** Она указывает Docker, что контекст сборки — текущая директория. 
> *Ошибка без точки:* `unable to prepare context: path ".": not found` или попытка скачать образ из интернета.
> *Флаг `-t`* — задает тег (имя) образу.

### Просмотр локальных образов
```bash
docker images
# или
docker image ls
```

### Анализ слоев и кэша
```bash
docker history <имя-образа>
```
> [!tip] 💡 Зачем это нужно
> Показывает, сколько весит каждый слой (столбец `SIZE`) и какие команды были выполнены. Помогает найти "тяжелые" слои для оптимизации.

## 🚀 Запуск и жизненный цикл контейнеров

### Запуск (одноразовый)
```bash
docker run --rm <имя-образа>
```
*Флаг `--rm` автоматически удаляет контейнер после его остановки, чтобы не засорять систему.*

### Запуск в фоне (для отладки)
```bash
docker run -d --name <имя-контейнера> <имя-образа> sleep 3600
```
> [!info] 🧩 Разбор флагов
> - `-d` (detach) — запуск в фоновом режиме (контейнер не занимает терминал).
> - `--name` — задает понятное имя контейнеру (иначе Docker сгенерирует случайное, вроде `funny_darwin`).
> - `sleep 3600` — "костыль", чтобы контейнер с Python-скриптом не завершился мгновенно, а жил 1 час, позволяя нам в него зайти.

## 🔍 Отладка и инспекция (Debugging)

### Зайти внутрь работающего контейнера
```bash
docker exec -it <имя-контейнера> /bin/sh
```
> [!info] 🧩 Разбор флагов
> - `exec` — выполнить команду в *уже запущенном* контейнере.
> - `-i` (interactive) — держать STDIN открытым.
> - `-t` (tty) — выделить псевдо-терминал (чтобы был красивый prompt).
> - `/bin/sh` (или `/bin/bash`) — оболочка, в которую мы попадаем. В `slim` образах часто нет `bash`, поэтому используем `sh`.

**Полезные команды внутри контейнера:**
```bash
ls -la       # Посмотреть файлы (проверить, сработал ли .dockerignore)
pwd          # Текущая директория
cat app.py   # Проверить содержимое файла
exit         # Выйти из контейнера (контейнер при этом продолжит работать)
```

## 🧹 Очистка и остановка

### Остановка фонового контейнера
```bash
docker stop <имя-контейнера>
```

### Удаление остановленного контейнера
```bash
docker rm <имя-контейнера>
```
> [!tip] 💡 Лайфхак
> Если использовать `docker run --rm ...`, то шаги `stop` и `rm` выполнять не нужно, Docker сделает это сам после завершения работы команды (например, после выполнения `python app.py`).

### Просмотр всех контейнеров (включая остановленные)
```bash
docker ps -a
```

## 📂 Работа с файлами контекста

### Создание `.dockerignore` (через терминал Linux)
```bash
cat << 'EOF' > .dockerignore
.venv/
venv/
__pycache__/
*.md
.git/
EOF
```
> [!warning] ⚠️ Почему это важно
> Без этого файла команда `COPY . .` затянет в образ гигабайты кэша, виртуальные окружения и `.git`. Это раздувает размер образа и ломает кэш Docker.
